HTML to PDF in Python: WeasyPrint vs ReportLab vs REST API

Sep 2026 · 9 min read · pdfsnap

Three libraries come up every time a Python developer needs HTML-to-PDF: WeasyPrint, ReportLab, and the "just call an API" approach. They solve different problems and fail in different ways. This post is the comparison I wish existed before I spent two days debugging Cairo font issues on a Lambda function.

Option 1: WeasyPrint

WeasyPrint is the most popular pure-Python option for converting HTML+CSS to PDF. It supports modern CSS, flexbox (mostly), and page-break rules. The output quality is genuinely good for documents — invoices, reports, anything print-oriented.

Installation

Here's where things get painful. WeasyPrint depends on Cairo, Pango, and GDK-PixBuf — C libraries that must be installed at the system level. On a Mac with Homebrew or on a Debian server this is manageable. On AWS Lambda or Google Cloud Functions, it becomes a packaging problem.

terminal
# macOS
brew install weasyprint

# Ubuntu/Debian
apt-get install -y python3-dev python3-pip libpango-1.0-0 libpangoft2-1.0-0 libcairo2

pip install weasyprint
Lambda warning: WeasyPrint needs native binaries (Cairo, Pango) that aren't in the Lambda runtime image. You'll need a custom container image or a Lambda layer with ~80MB of compiled libs. Cold-start penalty: 2–4 seconds on first invocation.

Basic usage

generate_pdf.py
from weasyprint import HTML, CSS

html_string = """
<html>
<head>
  <style>
    body { font-family: Helvetica, sans-serif; margin: 40px; }
    h1   { color: #1a1a2e; }
    .invoice-total { font-size: 24px; font-weight: bold; }
  </style>
</head>
<body>
  <h1>Invoice #1042</h1>
  <p>Due: 2026-10-01</p>
  <p class="invoice-total">Total: $1,200.00</p>
</body>
</html>
"""

# From string
pdf_bytes = HTML(string=html_string).write_pdf()
with open("invoice.pdf", "wb") as f:
    f.write(pdf_bytes)

# From URL (WeasyPrint fetches it)
pdf_bytes = HTML(url="https://example.com/report").write_pdf()

# With external CSS
css = CSS(string="@page { size: A4; margin: 20mm; }")
pdf_bytes = HTML(string=html_string).write_pdf(stylesheets=[css])

What WeasyPrint handles well

  • Print CSS (@page, page-break-before, orphans)
  • Most CSS 2.1 and a good subset of CSS 3
  • Flexbox for simple single-axis layouts
  • Custom fonts via @font-face (if font files are available)
  • SVG images embedded inline or as <img> src

Where WeasyPrint breaks

  • CSS Grid — not supported. Grid layouts fall back to block.
  • JavaScript — WeasyPrint has no JS engine. Dynamic content won't render.
  • Web fonts from CDN — Google Fonts URLs often fail in restricted environments (Lambda VPC, etc.).
  • Complex backgrounds and shadows — box-shadow is partially supported; results vary.
Verdict: WeasyPrint

Best for server environments where you can install system dependencies. Good CSS support, solid output quality for document-style PDFs. Bad choice for Lambda/serverless without a custom container. Not suitable for pages that require JavaScript rendering.

Option 2: ReportLab

ReportLab is the oldest Python PDF library — it's been around since the late 1990s. It's pure Python (no C library dependencies), which makes it easy to install anywhere. The trade-off: it does not render HTML directly. Instead you build PDFs programmatically via its Platypus document model, or parse simplified HTML via xhtml2pdf.

ReportLab + xhtml2pdf for HTML input

terminal
pip install reportlab xhtml2pdf
html_to_pdf_reportlab.py
from xhtml2pdf import pisa
import io

html_string = """
<html>
<head>
  <style>
    body { font-family: Helvetica; margin: 40px; }
    h1 { color: #1a1a2e; }
  </style>
</head>
<body>
  <h1>Invoice #1042</h1>
  <p>Due: 2026-10-01</p>
</body>
</html>
"""

output = io.BytesIO()
pisa_status = pisa.CreatePDF(html_string, dest=output)

if not pisa_status.err:
    with open("invoice.pdf", "wb") as f:
        f.write(output.getvalue())
else:
    print("PDF generation failed:", pisa_status.err)

The CSS problem

xhtml2pdf implements a subset of CSS 2.1 that is significantly smaller than WeasyPrint's. Flexbox, Grid, custom properties (var()), and most CSS 3 features are unsupported. If you're converting a modern web page, expect layout breakage. If you control the HTML source and keep it simple (tables for layout, inline styles), xhtml2pdf is workable.

Heads up: xhtml2pdf maps font-family to built-in PDF fonts (Helvetica, Times-Roman, Courier). Custom web fonts require embedding font files and registering them explicitly with ReportLab. This works but adds boilerplate.

When ReportLab makes sense

  • You need zero system dependencies (pure Python, pip-installable anywhere)
  • You're generating data-driven reports with simple tables and charts
  • You control the HTML source and can simplify it for xhtml2pdf compatibility
  • You need fine-grained control over individual PDF elements (graphics, custom layouts)
Verdict: ReportLab

Great for programmatic PDF generation when you control the source data. Poor choice for converting arbitrary or modern-CSS HTML. xhtml2pdf handles simple HTML well but fails on anything beyond CSS 2.1. The upside: zero system dependencies, works on Lambda without containers.

Option 3: REST API (pdfsnap)

Both WeasyPrint and ReportLab share a fundamental constraint: they run in your process, consuming your memory, with a rendering engine you have to keep updated and debugged. A REST API externalizes the rendering layer entirely — you send HTML, you get back a PDF binary.

pdfsnap runs a real Chromium instance behind a REST endpoint. This means full CSS 3 support, JavaScript execution, web font loading, and whatever a real browser renders — because it is a real browser.

Installation

terminal
pip install requests  # that's it

Basic usage

generate_pdf.py
import requests

html_string = """
<!DOCTYPE html>
<html>
<head>
  <style>
    @import url('https://fonts.googleapis.com/css2?family=Inter:wght@400;700&display=swap');
    body { font-family: 'Inter', sans-serif; margin: 40px; background: #fff; }
    h1   { color: #1a1a2e; font-size: 32px; }
    .total { font-size: 28px; font-weight: 700; color: #FF7A1A; }
    .grid  { display: grid; grid-template-columns: 1fr 1fr; gap: 16px; }
  </style>
</head>
<body>
  <h1>Invoice #1042</h1>
  <div class="grid">
    <div>Client: Acme Corp</div>
    <div>Due: 2026-10-01</div>
  </div>
  <p class="total">$1,200.00</p>
</body>
</html>
"""

resp = requests.post(
    "https://api.pdfsnap.dev/pdf",
    headers={
        "Authorization": "Bearer YOUR_API_KEY",
        "Content-Type": "application/json",
    },
    json={
        "html": html_string,
        "options": {
            "format": "A4",
            "margin": {"top": "20mm", "bottom": "20mm", "left": "16mm", "right": "16mm"},
            "printBackground": True,
        }
    }
)

resp.raise_for_status()
with open("invoice.pdf", "wb") as f:
    f.write(resp.content)

print(f"PDF saved ({len(resp.content):,} bytes)")

Converting a live URL instead

url_to_pdf.py
import requests

resp = requests.post(
    "https://api.pdfsnap.dev/pdf",
    headers={
        "Authorization": "Bearer YOUR_API_KEY",
        "Content-Type": "application/json",
    },
    json={
        "url": "https://app.example.com/reports/q3-2026",
        "options": {
            "format": "Letter",
            "waitUntil": "networkidle0",  # wait for all async data
            "printBackground": True,
        }
    }
)

resp.raise_for_status()
with open("q3_report.pdf", "wb") as f:
    f.write(resp.content)

Django / Flask integration

views.py (Django)
import requests
from django.http import HttpResponse
from django.template.loader import render_to_string

def invoice_pdf(request, invoice_id):
    invoice = Invoice.objects.get(pk=invoice_id)
    html = render_to_string("invoices/pdf_template.html", {"invoice": invoice})

    resp = requests.post(
        "https://api.pdfsnap.dev/pdf",
        headers={"Authorization": f"Bearer {settings.PDFSNAP_API_KEY}"},
        json={"html": html, "options": {"format": "A4", "printBackground": True}},
        timeout=30,
    )
    resp.raise_for_status()

    return HttpResponse(
        resp.content,
        content_type="application/pdf",
        headers={"Content-Disposition": f'attachment; filename="invoice-{invoice_id}.pdf"'},
    )
Verdict: REST API

Best for serverless environments, apps that need JavaScript rendering, and teams that don't want to maintain a browser binary. Zero system dependencies. Full CSS 3 + JS support. Adds a network call (~800ms p50 for most documents). Not ideal for air-gapped environments or extremely high-volume batch jobs where latency stacks up.

Which should you choose?

The decision tree is simpler than it looks:

  • Does your HTML use modern CSS (Grid, custom properties, animations) or JavaScript? → REST API. Neither WeasyPrint nor ReportLab will render it correctly.
  • Are you deploying to serverless (Lambda, Cloud Functions) without container support? → REST API or ReportLab. WeasyPrint's C dependencies are a packaging nightmare.
  • Do you need air-gapped / offline operation? → WeasyPrint (if you control the environment) or ReportLab (for simple HTML).
  • Are you generating data-driven reports from Python objects (not HTML templates)? → ReportLab directly (skip xhtml2pdf, use Platypus).
  • Do you want to convert a live URL as-rendered in a browser? → REST API or WeasyPrint. ReportLab can't fetch and render URLs.
The hidden cost of "free": WeasyPrint and ReportLab are open source and free to use. But the engineering time debugging system lib versions, writing a Docker layer, and handling font embedding across platforms adds up. For many teams, paying $19/mo to never think about it is the right call.

Summary

WeasyPrint is the right local library if you have a server with system-level dependencies and your HTML is document-oriented. ReportLab is the right local library if you need pure-Python portability and can simplify your HTML. A REST API is the right call for serverless environments, modern CSS, JavaScript rendering, and teams that want to stay out of the browser-maintenance business.

All three approaches work. The question is which failure mode you're willing to own.
