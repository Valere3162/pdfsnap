wkhtmltopdf Is Dead — Your API Alternatives in 2026

wkhtmltopdf was archived on GitHub in January 2023. No new releases, no security patches, and an increasingly unhappy CI/CD scanner every time you deploy. The migration is happening whether you plan for it or not. Here is what to move to.

The wkhtmltopdf Situation

Let's be factual about what happened. On January 11, 2023, the wkhtmltopdf GitHub repository was officially archived. The last release—version 0.12.6—shipped in June 2020. That means the project went three-plus years without a single patch before the maintainers formally declared it abandoned.

This matters for one concrete reason: wkhtmltopdf bundles a fork of Qt's WebKit from around 2016. That dependency chain includes multiple unpatched CVEs in libqt5 and the bundled OpenSSL variant. These are real vulnerabilities—server-side request forgery vectors, heap overflows in the HTML parser, and TLS downgrade opportunities—not theoretical ones.

Security tooling has caught up. If you are running Snyk, Dependabot, or Trivy in your CI/CD pipeline, you have probably already seen the warnings. Cloud providers are flagging the binary in container scans. Some enterprise security policies now block deployment of images that include it.

The bottom line

wkhtmltopdf is not "legacy but fine." It is an unpatched binary with known CVEs that no one is fixing because the project is archived. Every month you keep it is a month of compounding security debt.

The migration is already happening across the industry. The question is which tool to move to— and whether you want to manage infrastructure or use an API.

What You Actually Need in a Replacement

Before comparing options, it helps to be precise about requirements. Most teams are looking for four things:

  • Real Chromium rendering. wkhtmltopdf's WebKit from 2016 does not handle CSS Grid, CSS custom properties, modern web fonts, or JavaScript-rendered content. Anything built in the last four years probably renders wrong. You need a real, current Chromium engine.
  • No infrastructure to manage. wkhtmltopdf was already the "I don't want to run browsers" choice. If you replace it with Puppeteer on a VM you manage yourself, you have not actually solved the problem—you have made it bigger.
  • Serverless and Vercel compatible. Most new applications live on Vercel, Netlify, or AWS Lambda. Headless Chrome cannot be installed in a standard Vercel function. Your replacement needs to work within those constraints, not around them.
  • Consistent, pixel-identical output. PDFs are documents. They get emailed, signed, archived. "Works on my machine" is not acceptable—the output must be deterministic across environments.

The Alternatives Landscape

Self-hosted options

Gotenberg is a Docker container that wraps Chromium and LibreOffice behind a clean REST API. It is an excellent choice if you already run Kubernetes or Docker Compose and have ops capacity to manage it. It is not serverless-compatible—you are running a persistent container—and you own the upgrades, the scaling, and the availability.

Puppeteer / Playwright directly gives you maximum control and a genuine Chromium engine. It is also the most maintenance-intensive option: you manage the Chromium binary, handle the memory and concurrency issues that come with running browsers in production, and figure out your own queuing. It cannot run in a standard Vercel function. Good for teams with dedicated infrastructure engineering capacity.

WeasyPrint is a Python library with no JavaScript execution. It does an admirable job with CSS-heavy documents but breaks on any page that requires JS rendering. Not a general-purpose wkhtmltopdf replacement—more of a specialized tool for static, print-CSS-first documents.

Managed API options

pdfsnap is designed specifically for the serverless era: a single POST endpoint that accepts a URL or raw HTML body, returns a PDF, and uses @sparticuz/chromium—the same Chromium build that runs in AWS Lambda and Vercel Functions. Pay-per-render pricing with a free tier. No minimum commitment.

PDFShift is a well-established managed API with a clean interface. Pricing starts at $24/month on a credits model. Good documentation, reliable uptime history. Slightly more expensive for high-volume use cases.

API2PDF is a multi-engine service that supports wkhtmltopdf, Headless Chrome, and LibreOffice as rendering backends. Pricing starts around $50/month. The wkhtmltopdf option is still available—which is useful if you want a transitional period but undermines the security motivation for migrating.

Doppio is a newer entrant with solid developer experience and clean API design. Chromium-based. Pricing starts at $29/month with a minimum commitment. Worth evaluating if you want a managed service with a polished dashboard.

DocRaptor uses the Prince XML rendering engine rather than Chromium. Prince is exceptional for print CSS and structured documents (books, reports, financial statements). At $15/month entry pricing it is cost-effective. Not a fit if your documents rely on JavaScript execution or modern CSS that Prince does not support.

Migrating from wkhtmltopdf to pdfsnap

The actual code change is small. The conceptual change is larger: you are moving from a local binary subprocess to an HTTP call. Here is what that looks like in Node.js.

Node.js — URL to PDF

Before — wkhtmltopdf subprocess (Node.js) 
import { execFile } from 'node:child_process';
import fs from 'node:fs';

// Requires wkhtmltopdf installed on the host — breaks on Vercel/Lambda
execFile('wkhtmltopdf', [
  '--page-size', 'A4',
  '--margin-top', '15mm',
  'https://example.com/invoice/123',
  'output.pdf'
], (err) => {
  if (err) throw err;
  const pdf = fs.readFileSync('output.pdf');
  // ... ship the buffer
});
After — pdfsnap API (Node.js) 
// Works anywhere fetch() works — Vercel Edge, Lambda, Node, browsers
const res = await fetch('https://api.pdfsnap.dev/v1/pdf?format=A4', {
  method: 'POST',
  headers: {
    'Authorization': `Bearer ${process.env.PDFSNAP_KEY}`,
    'Content-Type': 'application/json',
  },
  body: JSON.stringify({ url: 'https://example.com/invoice/123' }),
});

const pdf = await res.arrayBuffer(); // ready to stream or store

Python — HTML body to PDF

Before — wkhtmltopdf subprocess (Python) 
import subprocess

# Spawns a local binary — not available in serverless environments
result = subprocess.run(
  ['wkhtmltopdf', '--page-size', 'A4', '-', '-'],
  input=html_bytes,
  capture_output=True
)
pdf_bytes = result.stdout
After — pdfsnap API (Python) 
import httpx  # or requests

resp = httpx.post(
  'https://api.pdfsnap.dev/v1/pdf',
  params={'format': 'A4'},
  headers={'Authorization': f'Bearer {PDFSNAP_KEY}'},
  json={'html': html_string},
)
pdf_bytes = resp.content

Common Migration Gotchas

Headers and footers

wkhtmltopdf used --header-html and --footer-html flags to inject separate HTML fragments. Chromium-based renderers use CSS print at-rules instead: @page with named strings and the position: running() property. This is more powerful—the header is part of the document—but requires updating your HTML template.

Page size flags

wkhtmltopdf --page-size A4 becomes ?format=A4 as a query parameter in the pdfsnap API. Supported values: A4, Letter, Legal, A3, A5. Custom dimensions are available via ?width=&height= in millimeters.

URL rendering

wkhtmltopdf https://example.com output.pdf maps directly to { "url": "https://example.com" } in the request body, or you can use the ?url= query parameter for GET requests. The key difference: pdfsnap's Chromium will actually execute JavaScript and wait for the page to reach a network-idle state before capturing the PDF, so JS-rendered content will be present in the output.

Margin defaults

wkhtmltopdf defaults to 10mm margins. pdfsnap inherits Chromium's default, which is roughly equivalent. If your documents have precise margin requirements, use @page { margin: 15mm; } in your CSS rather than relying on API parameters.
