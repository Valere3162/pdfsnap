How to Generate PDF Reports in Django (2026 Guide)

Sep 2026 · 9 min read · PDFsnap

Django makes almost everything easy — except PDF generation. Generating an invoice, report, or certificate from a Django view means picking between libraries with broken CSS support, system-level binary dependencies, and Docker build failures. This guide covers every realistic option in 2026 and shows you working code for each one.

The four options

There are four real approaches to generating PDFs in Django in 2026:

  1. xhtml2pdf — pure Python, but frozen in 2015-era CSS
  2. WeasyPrint — modern CSS support, but painful to install
  3. Headless Chrome via subprocess — full CSS support, binary dependency
  4. PDFsnap REST API — no installs, no binaries, works everywhere

Jump to the comparison table if you just want a quick decision. Otherwise, read on — the install stories matter.

Option 1: xhtml2pdf

xhtml2pdf (formerly pisa) is the path of least resistance. It's pure Python, installs with pip, and has been around forever. The problem is it implements HTML 4 + CSS 2.1. In 2026, your templates probably use flexbox, CSS variables, or web fonts — none of which xhtml2pdf supports.

Install

terminal
pip install xhtml2pdf

Django view

views.py
# views.py
import io
from django.http import HttpResponse
from django.template.loader import get_template
from xhtml2pdf import pisa

def invoice_pdf(request, invoice_id):
    invoice = Invoice.objects.get(pk=invoice_id)
    template = get_template('invoices/invoice.html')
    html = template.render({'invoice': invoice})

    result = io.BytesIO()
    pdf = pisa.pisaDocument(io.BytesIO(html.encode('UTF-8')), result)

    if not pdf.err:
        return HttpResponse(result.getvalue(), content_type='application/pdf')

    return HttpResponse('PDF generation failed', status=500)
When to use xhtml2pdf

Simple documents with minimal styling. Internal admin tools where visual fidelity doesn't matter. Projects that can't add any system dependencies whatsoever. Anything else — move to option 2 or 4.

Option 2: WeasyPrint

WeasyPrint is the best pure-Python option for CSS fidelity. It supports CSS 3, web fonts, flexbox (partially), and produces clean output. The trade-off is installation complexity: WeasyPrint requires Pango, Cairo, and a collection of system libraries that vary by OS and Linux distribution.

Install

terminal
# macOS
brew install pango

# Ubuntu/Debian
apt-get install -y libpango-1.0-0 libpangoft2-1.0-0 libffi-dev

# Then Python package
pip install weasyprint
Lambda / serverless warning

WeasyPrint will not run on AWS Lambda out of the box. The Pango/Cairo libraries aren't in the Lambda execution environment. You need a custom Lambda layer or a container image. Factor this into your architecture before committing.

Django view

views.py
# views.py
from django.http import HttpResponse
from django.template.loader import render_to_string
from weasyprint import HTML, CSS
from weasyprint.text.fonts import FontConfiguration

def invoice_pdf(request, invoice_id):
    invoice = Invoice.objects.get(pk=invoice_id)
    html_string = render_to_string('invoices/invoice.html', {'invoice': invoice})

    font_config = FontConfiguration()
    html = HTML(string=html_string, base_url=request.build_absolute_uri('/'))

    pdf_bytes = html.write_pdf(font_config=font_config)

    response = HttpResponse(pdf_bytes, content_type='application/pdf')
    response['Content-Disposition'] = f'attachment; filename="invoice-{invoice_id}.pdf"'
    return response
When to use WeasyPrint

Good CSS support matters, you control the deployment environment, and it's not serverless. If you run on a standard VPS or EC2 instance where you can install system packages, WeasyPrint is the best self-hosted option.

Option 3: Headless Chrome via subprocess

If you need perfect CSS rendering — the same output the user sees in Chrome — the only real answer is headless Chrome. You can shell out to it from Django, but this approach has significant operational overhead: you need Chrome installed in your environment, you need to manage subprocess failures, and it's slow for concurrent requests.

Install

terminal
# Ubuntu — install Chrome
wget -q -O - https://dl-ssl.google.com/linux/linux_signing_key.pub | apt-key add -
echo "deb http://dl.google.com/linux/chrome/deb/ stable main" >> /etc/apt/sources.list.d/google.list
apt-get update && apt-get install -y google-chrome-stable

Django view

views.py
# views.py
import subprocess
import tempfile
import os
from django.http import HttpResponse
from django.template.loader import render_to_string

def invoice_pdf(request, invoice_id):
    invoice = Invoice.objects.get(pk=invoice_id)
    html_string = render_to_string('invoices/invoice.html', {'invoice': invoice})

    with tempfile.NamedTemporaryFile(suffix='.html', delete=False) as f:
        f.write(html_string.encode('utf-8'))
        html_path = f.name

    pdf_path = html_path.replace('.html', '.pdf')

    try:
        subprocess.run([
            'google-chrome', '--headless', '--disable-gpu',
            '--no-sandbox', '--print-to-pdf=' + pdf_path,
            html_path
        ], check=True, timeout=30)

        with open(pdf_path, 'rb') as f:
            pdf_bytes = f.read()

        response = HttpResponse(pdf_bytes, content_type='application/pdf')
        response['Content-Disposition'] = f'attachment; filename="invoice-{invoice_id}.pdf"'
        return response
    finally:
        os.unlink(html_path)
        if os.path.exists(pdf_path):
            os.unlink(pdf_path)
Do not use this in production without a queue

Each PDF request spawns a full Chrome process. Under concurrent load, you will exhaust memory. If you go this route, offload PDF generation to a Celery task with a bounded concurrency worker, not the request/response cycle.

Option 4: PDFsnap REST API (recommended for most cases)

The cleanest approach for most Django projects is to offload PDF rendering to a dedicated API. No system dependencies, no binary management, works identically in development, staging, and production — including serverless and containers with minimal layers.

Install

terminal
pip install requests  # already in most Django projects

Django view

views.py
# views.py
import requests
from django.conf import settings
from django.http import HttpResponse
from django.template.loader import render_to_string

PDFSNAP_API_KEY = settings.PDFSNAP_API_KEY

def invoice_pdf(request, invoice_id):
    invoice = Invoice.objects.get(pk=invoice_id)
    html_string = render_to_string('invoices/invoice.html', {'invoice': invoice})

    response = requests.post(
        'https://api.pdfsnap.dev/v1/pdf',
        headers={
            'Authorization': f'Bearer {PDFSNAP_API_KEY}',
            'Content-Type': 'application/json',
        },
        json={
            'html': html_string,
            'options': {
                'format': 'A4',
                'margin': {'top': '20mm', 'bottom': '20mm', 'left': '16mm', 'right': '16mm'},
                'printBackground': True,
            }
        },
        timeout=30,
    )
    response.raise_for_status()

    return HttpResponse(
        response.content,
        content_type='application/pdf',
        headers={'Content-Disposition': f'attachment; filename="invoice-{invoice_id}.pdf"'}
    )

Store the key in settings.py

settings.py
import os

PDFSNAP_API_KEY = os.environ.get('PDFSNAP_API_KEY', '')

Adding a Celery task for high-volume use

If you're generating many PDFs (bulk invoice runs, report exports), offload to a background task:

tasks.py
# tasks.py
from celery import shared_task
import requests
from django.conf import settings
from django.template.loader import render_to_string
from django.core.files.base import ContentFile

@shared_task
def generate_invoice_pdf(invoice_id):
    from .models import Invoice
    invoice = Invoice.objects.get(pk=invoice_id)
    html_string = render_to_string('invoices/invoice.html', {'invoice': invoice})

    response = requests.post(
        'https://api.pdfsnap.dev/v1/pdf',
        headers={'Authorization': f'Bearer {settings.PDFSNAP_API_KEY}'},
        json={'html': html_string, 'options': {'format': 'A4', 'printBackground': True}},
        timeout=30,
    )
    response.raise_for_status()

    # Save to model's FileField
    invoice.pdf_file.save(
        f'invoice-{invoice_id}.pdf',
        ContentFile(response.content),
        save=True,
    )
    return invoice.pdf_file.url

Common Django gotchas

Relative URLs in templates

When rendering templates to HTML for PDF generation, static file URLs like /static/logo.png won't resolve unless you build the absolute URL. Pass request.build_absolute_uri('/') to WeasyPrint's base_url parameter, or use absolute CDN URLs in your PDF templates.

Inline CSS only for xhtml2pdf

xhtml2pdf does not load external stylesheets. All styles must be inline or in a <style> block in the template. Create a separate template for PDF output rather than reusing your web templates.

Font loading

Web fonts (Google Fonts, custom woff2 files) require internet access during render time. For production, embed fonts as base64 data URIs or use a system font stack. The PDFsnap API handles web fonts automatically — fonts load in its headless browser just as they would for a user.

Page breaks

Control page breaks with CSS: page-break-before: always, page-break-inside: avoid. Both WeasyPrint and Chrome-based renderers respect these. xhtml2pdf has limited page break support.
